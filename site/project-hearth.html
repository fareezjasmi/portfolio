Project Hearth

A civilization sandbox that runs entirely in one browser tab. Ten villagers decide their own work, eat, rest, marry and raise children while homes, shops and roads get built around them, and a second civilization, conquest objectives and physics-driven combat layer on top in the other mode.

Status
Live, both modes playable. Type-check and production build pass; no automated gameplay tests and no balance tuning yet.
Simulation
TypeScript with no Three.js dependency: people, needs, tasks, navigation and town growth are plain serialisable state
Frontend
TypeScript, Three.js, Vite. Procedural geometry, no art assets and no asset pipeline
Physics
Rapier (WASM) driving eleven-part articulated ragdolls, loaded as a separate chunk only when conquest runs
AI layer, optional
TypeSafe Jev through the official @typesafe-ai/sdk, loopback-only. A deterministic local policy is the default and the fallback

What it sets out to do

  • Make a simulation interesting without a backend. Movement, work, resource arithmetic, pathfinding and animation are all solved locally in the tab. Nothing needs an account, a database or a running service, which is what makes a free static deploy honest rather than a compromise.
  • Keep the AI narrow and checkable. The model never chooses an action freely. The simulation offers a bounded list of feasible action-and-target options, the model returns one of those identifiers plus an urgency score, and the answer is rejected unless it matches an offered option. Everything is validated again against inventory, reservations, reachability and prerequisites before it changes the world.
  • Show the decision, not just its result. Every choice is labelled by source, and every log entry opens its original input snapshot: the trigger, the options offered, the target chosen, confidence, priority and latency. Failed model requests fall back visibly instead of being smoothed over.
  • Let systems interfere with each other. Economy, households, growth and combat share one clock and one state. Food shortages stop births, a threatened capital shelters civilians, and a recruited soldier leaves their job and has to be replaced.
  • Keep it honest. Where something is unbuilt or untested, the page and the README say so instead of implying more than was verified.

How a villager decides

  1. The simulation advances on a fixed step. Needs, energy, hunger, inventory, reservations and task state machines all move on that same clock, and a pause or a speed change moves the clock, not the rendering.
  2. The scheduler decides who is allowed to think. Opportunities are staggered, at most one decision is in flight per person, results that arrive after the situation changed are discarded, and model requests are spaced by at least three real seconds across all ten villagers.
  3. The context builder gathers scoped observations: needs, current task, carried inventory, relevant memories and relationships, village priorities and worker coverage. From those it builds the feasible action-and-target candidates, each with a local utility score.
  4. The provider answers. The local policy sorts candidates by utility and is always available. When a Jev key is connected and enabled, the request instead goes to the loopback server, which asks the model to choose one offered option and rate urgency.
  5. The simulation validates the result against the present state and applies it only at a tick, recording the decision, its source and its snapshot.

Local execution never calls a model for movement, work ticks, resource arithmetic, animations or pathfinding. Nothing is awarded because a decision was selected: wood and food have to be harvested or bought by a villager who is actually there.

Delivery and hosting

  • Subpath build. Vite emits root-relative asset URLs by default, which 404 on a GitHub Pages project site. The production build sets base to /project-hearth/ while development keeps /, so the loopback server and the usual local URL are unchanged.
  • One workflow, no manual uploads. A push to main runs Node 22, npm ci, npm run build, uploads the artifact and deploys it. dist/ is gitignored and built in CI, so the published bundle cannot silently drift from the source.
  • The AI key path is closed on purpose. The connection server is loopback-only, so no static host can serve it. The client probes the status endpoint once, and when no server answers it disables key entry and explains why, rather than showing a form that cannot work.
  • Scope, stated plainly. This is a deploy pipeline, not a mobile release pipeline: no code signing, no matrix builds across platforms and no store uploads yet. Those are the next CI/CD additions rather than things this project already does.

Limitations

  • In memory only. Refreshing resets the village. There is no save, no load, no state transfer between the two modes, and no full generational aging.
  • Compile-checked, not play-tested. TypeScript and the production build pass, and both modes were verified to load and render in a browser. Balance, emergent behaviour, family growth and the traffic fix were not tuned or playtested, and there are no automated gameplay tests.
  • The AI path itself is unverified end to end, because it needs a live TypeSafe key to exercise.
  • Conservative crowd navigation. Walkers may yield or abandon a blocked task before choosing another; it is not a full RTS navigation mesh.
  • Bounded by design. Twelve memories per villager, the last 120 decisions and 80 world events retained, 45 shown, sixteen decision traces per person, and a cap of forty residents on this map size.

Key decisions

Local policy first, model second
The deterministic policy is the default, not a degraded mode. It keeps survival behaviour responsive, removes the latency and cost from the common path, and gives the model a fallback that is already good instead of an error state. Model requests are then a bounded, visible luxury rather than a dependency.
A bounded choice, not free text
Letting the model name actions and coordinates invites silent invalid states. It receives a scoped option list and returns one identifier plus urgency; the server checks the shape and the offered identifier, and the simulation re-checks feasibility against the world. A malformed or stale answer is discarded.
The renderer is a consumer
Simulation state holds no Three.js objects. Positions and actions are plain data, so rendering can be swapped, throttled or moved without touching behaviour, which is also what makes the visuals safe to fail.
Physics is cosmetic
Ragdolls never decide damage or navigation. Combat resolves on the simulation tick; knockdowns are drawn from it. That keeps a 2 MB WebAssembly engine out of the correctness path and lets it load lazily, only for conquest.
Static hosting without lying about it
The honest static site is the fully playable one. Rather than pretending the AI mode works everywhere, the hosted build detects the missing server and says so, which is cheaper than running a service nobody needs and clearer for anyone clicking the demo.

What is next

  • Save and load, which is the prerequisite for everything generational.
  • Automated gameplay tests: deterministic seeded runs that assert economy and population outcomes, so balance changes stop being eyeballed.
  • A playtesting and balance pass on family growth, cooperative construction and conquest combat, which are currently compile-checked only.
  • Release engineering, if this becomes a distributed desktop or mobile build: signing, matrix builds and store tracks, which is the same pipeline work as my mobile projects.
