Pixel Forge

A team of AI agents that turns a one-paragraph game idea into a playable Three.js game, with every step streamed live to the browser.

How a run works

  1. The browser posts an idea. The API creates the run record, enqueues a job and returns 202 straight away.
  2. The browser opens a Server-Sent Events stream. The API polls storage for new events and forwards them, with a keep-alive every 15 seconds.
  3. A worker takes the job and runs the agents: a Producer writes the brief, Gameplay, World and Art specialists run concurrently, a Critic reviews, and the Producer finalises a GameSpec.
  4. A Technical Director hands off to a Three.js Builder, which writes the game in TypeScript.
  5. The source goes to the offline builder sandbox. QA reviews the real build output, and a Fix Engineer gets at most two correction passes.
  6. The built game is published to artifact storage and served from the CDN.

One environment variable per concern picks the implementation. A compose overlay runs the real boto3 code paths against a local moto server, and CI runs the end-to-end smoke test in both modes.

Treating AI-written code as untrusted

A prompt-injected or simply wrong model can write arbitrary TypeScript, so the build step is treated like running code from a stranger.

  • No network, no credentials. Builds run offline. On AWS each build task sits in isolated subnets with no internet route, and model keys live only in the worker.
  • Fixed dependencies. The game scaffold is pinned and baked into the builder image, so nothing is installed at build time.
  • Least privilege and hard limits. A non-root, read-only environment with CPU, memory and time limits, and a task role that can only reach its own build input and output.
  • Disposable. One short-lived container per build.

Key decisions

Fargate, not Lambda
A run chains about ten LLM calls and up to three builds, and takes several minutes, sometimes more than fifteen, beyond Lambda's hard limit. The worker autoscales on SQS queue depth, and the same container runs locally.
SQS between API and workers
Deploys and crashes no longer lose runs, and web and agent capacity scale separately. Delivery is at least once, so the worker is idempotent per run, with a DLQ for poison messages.
DynamoDB, not RDS
The access pattern is "append an event" and "read events after N". One on-demand table with an atomic per-run counter gives ordered, gap-free events and costs close to nothing at low traffic.
One CloudFront origin
The app, /api/* and /games/* share one domain: no CORS preflight, one certificate, one WAF attach point.
Stream by polling storage
Works across processes, replicas and restarts with no extra infrastructure, and replay and resume come free.
